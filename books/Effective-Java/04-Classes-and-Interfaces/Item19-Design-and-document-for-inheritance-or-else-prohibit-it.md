# Item 19: Design and Document for Inheritance, or Else Prohibit It

## Documenting Self-Use of Overridable Methods
###
- 🔑 **Overridable** = nonfinal *and* public or protected
- Class must document precisely the effects of overriding any method
- For each public/protected method, state **which** overridable methods it invokes, **in what sequence**, and how each result affects later processing
- 📌 Document *any* circumstances of invoking an overridable method (e.g. background threads, static initializers)

### The `@implSpec` Mechanism
- Description placed at end of doc comment, in an **"Implementation Requirements"** section
- Generated by the Javadoc tag `@implSpec`
- Describes the method's inner workings
- ⚠️ Added in Java 8, heavy in Java 9; Javadoc still ignores it unless you pass `-tag "apiNote:a:API Note:"`

### Example: `AbstractCollection.remove`
- Doc states the implementation iterates over the collection looking for the element
- Removes it via the iterator's `remove` method
- 💡 Leaves no doubt that overriding `iterator` affects `remove`'s behavior
- Throws `UnsupportedOperationException` if iterator's `remove` is unimplemented
- Contrast Item 18: subclasser of `HashSet` couldn't tell if overriding `add` affected `addAll`

### The Encapsulation Tradeoff
- Good docs should say *what* a method does, not *how*
- ⚠️ Documenting self-use breaks this rule deliberately
- 💡 Unfortunate consequence: **inheritance violates encapsulation**

## Providing Hooks via Protected Members
### Why Hooks Matter
- A class may need to expose its internals as judiciously chosen **protected methods** or, rarely, **protected fields**
- Lets programmers write efficient subclasses without undue pain

### Example: `AbstractList.removeRange`
- `protected void removeRange(int fromIndex, int toIndex)`
- Called by the `clear` operation on a list and its sublists
- Overriding it can substantially speed up `clear`
- 📊 Default impl uses a list iterator + repeated `next`/`remove`; quadratic time if `remove` is linear
- 💡 Of no interest to end users — exists solely so subclasses get a fast sublist `clear`
- Without it, subclasses face quadratic performance or must rewrite `subList` from scratch

### Choosing Which Protected Members to Expose
- ❌ No magic bullet — think hard, guess, then test
- ✅ Expose **as few as possible** — each is a commitment to an implementation detail
- ⚠️ But not too few — a missing member can make the class unusable for inheritance

### Test by Writing Subclasses
- 📌 The *only* way to validate a class designed for inheritance
- Omitting a crucial protected member makes the gap painfully obvious
- If no subclass uses a member, make it **private**
- 📊 Experience: **three subclasses** usually suffice; at least one by someone other than the author
- ⚠️ Must test *before* release — you commit **forever** to documented self-use and protected members
- ⚠️ Inheritance docs clutter the normal API docs; few tools separate the two

## Restrictions a Class Must Obey
### Constructors Must Not Invoke Overridable Methods
- ⚠️ Directly or indirectly — violation causes program failure
- Superclass constructor runs *before* subclass constructor
- 💡 The overriding method runs before subclass init completes
- Broken example: `Super()` calls `overrideMe()`; `Sub` overrides it to print a `final Instant`
- 📊 Prints `null` first because the field isn't initialized yet — observes a `final` field in two states
- Would throw `NullPointerException` if `overrideMe` called any method on the field
- ✅ Safe to call **private**, **final**, and **static** methods from a constructor

### `Cloneable` and `Serializable` Difficulties
- ⚠️ Generally a bad idea to implement either in a class designed for inheritance — heavy burden on extenders
- 🔑 `clone` and `readObject` behave like constructors → must **not** invoke overridable methods
- `readObject`: overriding method runs before subclass state is deserialized
- `clone`: overriding method runs before subclass `clone` fixes the clone's state — can damage the *original* object too
- 📌 If `Serializable` with `readResolve`/`writeReplace`, make those methods **protected**, not private (private ones are silently ignored by subclasses)
- See Item 13 and Item 86 for safely enabling these interfaces

## When to Allow vs Prohibit Inheritance
### Clear Cases
- ✅ Right thing: **abstract classes**, including skeletal implementations (Item 20)
- ❌ Wrong thing: **immutable classes** (Item 17)

### Ordinary Concrete Classes Are Dangerous
- ⚠️ Traditionally neither final nor designed for subclassing
- Each internal change risks breaking existing subclasses
- 📌 Subclassing-related bug reports are a real, common problem

### Prohibiting Subclassing — Two Ways
- ✅ Declare the class **`final`** (easier)
- ✅ Make all constructors private/package-private + add **public static factories** (Item 17) — allows internal subclasses
- 💡 If the class implements an essence-capturing interface (`Set`, `List`, `Map`), feel no compunction prohibiting subclassing
- The **wrapper class pattern** (Item 18) is a superior alternative for augmenting functionality

### If You Must Allow Inheritance
- 📌 Eliminate the class's self-use of overridable methods entirely, and document that fact
- 💡 Then overriding a method never affects any other method — reasonably safe to subclass
- 🔑 Mechanical technique: move each overridable method's body into a private **helper method**; have the overridable method call the helper; replace internal self-uses with direct calls to the helper

## Key Takeaways
- Designing for inheritance is hard work: document **all** self-use patterns and commit to them for the class's lifetime
- To enable efficient subclasses you may have to export protected methods — expose as few as possible, validated by writing ~3 subclasses
- Constructors (and `clone`/`readObject`) must never invoke overridable methods — only private, final, or static ones are safe
- 📌 Unless there is a real need for subclasses, **prohibit inheritance**: declare the class `final` or remove accessible constructors
