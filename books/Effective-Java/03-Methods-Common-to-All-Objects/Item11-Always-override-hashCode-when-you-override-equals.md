# Item 11: Always Override `hashCode` When You Override `equals`

## The Core Rule
- Override **`hashCode`** in *every* class that overrides **`equals`**
- ⚠️ Failing to do so violates the `hashCode` general contract
- 💥 Breaks behavior in hash-based collections: `HashMap`, `HashSet`

## The `hashCode` Contract
### Consistency
- 🔑 Repeated calls return the *same value* during one execution
- Holds only if fields used in `equals` are unmodified
- 📌 Value need **not** be consistent across different executions
### Equality Implication
- 📌 If two objects are *equal* per `equals`, their `hashCode`s **must** be equal
- 🔑 This is the provision violated when you skip `hashCode`
### Inequality (best-effort)
- Unequal objects are *not required* to have distinct hash codes
- 💡 But distinct codes for unequal objects improve hash-table performance

## Why Skipping It Breaks Things
### The `PhoneNumber` Failure
- `Object.hashCode` treats two logically equal instances as unrelated
- Returns two seemingly random numbers instead of equal ones
- Example: `m.put(new PhoneNumber(707,867,5309), "Jenny")`
  - `m.get(new PhoneNumber(707,867,5309))` returns **`null`**, not `"Jenny"`
- 💡 Insert instance and retrieve instance are *distinct but equal* objects
### Mechanism of Failure
- Unequal hash codes → `get` searches a *different bucket* than `put` used
- ⚠️ Even in the same bucket, `HashMap` caches each entry's hash code
  - Skips equality check entirely when cached codes don't match

## Writing a Good `hashCode`
### ❌ The Worst Legal Implementation
- `@Override public int hashCode() { return 42; }`
- ✅ Legal: equal objects get equal codes
- ❌ Atrocious: *every* object hashes to one bucket
- Hash tables degenerate to linked lists → **linear becomes quadratic time**
### 🔑 Goal of a Good Hash Function
- Produce unequal codes for unequal instances (3rd contract part)
- Ideal: distribute instances *uniformly* across all `int` values
- A fair approximation is achievable with a simple recipe

## The Recipe (page 51)
### Step 1 — Initialize
- Declare `int result`, set to hash code `c` of the *first* significant field
- 🔑 *Significant field* = a field that affects `equals` comparisons
### Step 2 — For Each Remaining Significant Field
#### 2.a Compute field hash code `c`
- Primitive → `Type.hashCode(f)` (boxed primitive class)
- Object reference (compared via `equals`) → recursively call `hashCode`
  - Complex comparison → hash a *canonical representation*
  - `null` field → use `0` (traditional)
- Array → treat each significant element as a separate field
  - All elements significant → use `Arrays.hashCode`
  - No significant elements → use a constant, *preferably not 0*
#### 2.b Combine into result
- `result = 31 * result + c;`
### Step 3 — Return
- `return result;`
### Verification
- Ask: do equal instances have equal hash codes?
- ✅ Write unit tests to confirm
- 📌 Omit tests only if `equals`/`hashCode` were generated by **AutoValue**

## Field Selection Rules
- ✅ May *exclude derived fields* (computable from included fields)
- ⚠️ Must *exclude* fields not used in `equals`, or you violate provision 2
- ⚠️ Don't drop *significant* fields to gain speed — poor quality can make tables unusable
  - Clustered data differing only in ignored regions → quadratic time
  - 📊 Pre-Java 2 `String` hashed ≤16 evenly-spaced chars → pathological on URLs

## Why `31`?
- Multiplication makes result depend on *field order*
- 💡 Without it, all anagrams of a `String` share one hash code
- `31` is an *odd prime*
  - Even + overflow would lose info (×2 ≡ a shift)
  - Prime is traditional; advantage less clear
- Optimizable: `31 * i == (i << 5) - i` — modern VMs do this automatically

## Implementations for `PhoneNumber`
### Typical Recipe Version
```java
@Override public int hashCode() {
  int result = Short.hashCode(areaCode);
  result = 31 * result + Short.hashCode(prefix);
  result = 31 * result + Short.hashCode(lineNum);
  return result;
}
```
- Deterministic on the 3 significant fields → equal instances, equal codes
- ✅ Simple, fast, good dispersion; on par with JDK value types
- ⚠️ Not state-of-the-art — for fewer collisions see Guava's `com.google.common.hash.Hashing`
### One-Line Version
```java
@Override public int hashCode() {
  return Objects.hash(lineNum, prefix, areaCode);
}
```
- Uses `Objects.hash(...)`, quality comparable to the recipe
- ⚠️ Slower: array creation for varargs, plus boxing/unboxing
- 📌 Recommended only when performance is *not* critical
### Cached / Lazily Initialized Version
```java
private int hashCode; // auto-initialized to 0
@Override public int hashCode() {
  int result = hashCode;
  if (result == 0) {
    result = Short.hashCode(areaCode);
    result = 31 * result + Short.hashCode(prefix);
    result = 31 * result + Short.hashCode(lineNum);
    hashCode = result;
  }
  return result;
}
```
- 💡 For *immutable* classes where hashing cost is significant
- Mostly-used-as-keys → compute at construction time
- Otherwise → lazily initialize on first call
- ⚠️ Lazy init requires care to stay thread-safe (Item 83)
- 📌 Initial field value (`0`) must not equal a common instance's hash code

## Keep the Specification Loose
- ✅ Don't document the exact value `hashCode` returns
- 💡 Clients then can't depend on it → you retain freedom to change it
- ⚠️ `String` and `Integer` *do* specify exact values — a mistake we live with
  - Impedes improving the hash function in future releases

## Key Takeaways
- 📌 Override `hashCode` *every time* you override `equals`, or programs misbehave
- 🔑 Equal objects **must** have equal hash codes; do a reasonable job spreading unequal ones
- The page-51 recipe is easy (if tedious) and yields JDK-quality hashes
- ⚠️ Never exclude significant fields or hard-code a constant to "optimize"
- ✅ Leave the return value unspecified to preserve future flexibility
- 💡 **AutoValue**, and IDEs, can generate `equals`/`hashCode` for you
